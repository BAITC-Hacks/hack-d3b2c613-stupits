# «Аким на 5 часов» — материалы для дизайнера

Снимок интерфейса и данных: 23 сентября 2026 года.

Пользователь играет роль акима Астаны: выбирает **ровно 5 проектов из 14**,
распределяет **100 условных единиц бюджета** и смотрит, как изменится жизнь
районов. Важен не только высокий городской балл, но и помощь слабым районам.
Это учебная модель с условными показателями, а не прогноз реальных расходов.

Главный путь: **изучить районы → собрать план → увидеть результат → прочитать
разбор → сравнить с альтернативой**. Компоновку можно менять, сохранив действия,
состояния и обязательные сведения, описанные ниже.

## Что лежит в этой папке

| Файл | Что внутри | Для какого макета |
| --- | --- | --- |
| [sample_baseline.json](sample_baseline.json) | Настоящий ответ `baseline()`: город до проектов | Первый вход, карта и профиль района |
| [sample_simulation.json](sample_simulation.json) | Настоящий ответ `simulate()` для примера из ТЗ | Успешный расчёт, таблицы, изменения, синергии |
| [sample_invalid.json](sample_invalid.json) | Настоящий ответ `validate()` с двумя нарушениями | Ошибки плана |
| [sample_optimize.json](sample_optimize.json) | Настоящий ответ `optimize(top_n=5)` без дополнительных ограничений | Пять лучших планов |
| [sample_advisor.json](sample_advisor.json) | Настоящий офлайн-ответ `ask_advisor()`: текст и журнал | Авторазбор, чат, раскрытый журнал, офлайн-режим |
| [generate_samples.py](generate_samples.py) | Скрипт обновления всех пяти JSON | Передача разработчику, воспроизводимость |

Примеры не нарисованы вручную: их вернули текущие движок и советник. Они
сохранены целиком, без переименования полей. `sample_invalid.json` содержит
только `valid` и `errors`: отсутствие Score здесь ожидаемо.

Основные справочники находятся в [data/city_data.json](../../data/city_data.json):
`districts` — районы, `indicators` — показатели, `measures` — полный каталог
проектов, `directions` — названия направлений, `rules` и `incompatibilities` —
правила. В `sample_simulation.measures` есть только выбранные проекты, не все 14.

В таблицах ниже `districts[]` означает запись нужного района в списке.
Районы связываются по `id`, проекты — по `measure`/`id`, а не по порядку строк.
`indicators.<код>` означает показатель, например `indicators.S1`.

## Общая шапка

Шапка видна над четырьмя вкладками: «Город и проекты», «Результаты»,
«Лучшие планы», «ИИ-советник».

| Элемент | Что видит пользователь | Откуда данные |
| --- | --- | --- |
| Название и задача | «Аким на 5 часов», краткое объяснение цели | Название продукта; лимиты из справочника |
| Текущая оценка города | До расчёта — база; после — Score выбранного плана | `sample_baseline.score` / `sample_simulation.score` |
| Изменение оценки | Подпись со знаком, например `+3,99` | `sample_simulation.delta.score` |
| Базовая оценка | В этом снимке `52,56` | `sample_baseline.score` |
| Остаток бюджета | Например, «5 из 100 у.е.» | После расчёта — `budget_left` и `budget`; при сборке — бюджет минус цены выбранных мер |
| Полоса бюджета | Остаток: от 0 до 100%; в начале 100%, у примера 5% | Доля оставшегося бюджета |
| Счётчик | «Выбрано N из 5» | Текущий выбор и `num_decisions` из справочника |
| Статус | Исходное состояние / результат плана; сообщения о проблемах | Наличие расчёта, ошибки и состояние подключения |

**Score — городской итог, D — оценка отдельного района. Это разные величины.**
Показатели и D имеют шкалу 0–100; Score следует показывать самостоятельным
числом, не процентом и без искусственного обрезания по этой шкале.

Числа в JSON записаны с точкой; в русском интерфейсе — с запятой. Для оценок
обычно нужны два знака после запятой. Базу нельзя навсегда зашивать в дизайн:
52,56 — значение текущих данных, в приложении оно читается из ответа движка.

Изменение Score **не пересчитывать из округлённых цифр на карточках**.
В реальном примере итог 56,54, база 52,56, а `delta.score` равен 3,99: движок
считает разницу до округления. Интерфейс уже поясняет это под результатом.

## Вкладка «Город и проекты»

### Карта районов

Районы окрашены по D: красный соответствует низкой оценке, жёлтый — середине
шкалы, зелёный — высокой. Легенда: 0 / 50 / 100. Это непрерывная шкала D,
а не статусы отдельных показателей из профиля.

При наведении показываются название района, D и три самых слабых показателя
с понятными названиями и значениями. Нажатие на район открывает его профиль.
Есть переключатель объёмной карты: выше D — выше полигон. После расчёта
цвета, высоты и подсказки обновляются по новому состоянию.

Данные: до расчёта `sample_baseline.districts[].D`, после —
`sample_simulation.districts[].D_after`. Для слабых показателей используются
`indicators.<код>.value` в базе и `indicators.<код>.after` после расчёта.

Если файл карты отсутствует, повреждён или не содержит всех районов,
показываются **пять карточек районов** с D, изменением и кнопкой «Открыть район».
Выбор района и остальная игра должны продолжать работать.

### Профиль выбранного района

Пользователь может выбрать район и в выпадающем списке, независимо от карты.
Профиль содержит название, короткое описание проблемы, долю населения, D
и все десять показателей. У каждого показателя — значение, понятный статус,
после расчёта также изменение относительно базы.

| Данные профиля | База | После расчёта |
| --- | --- | --- |
| Название, описание, доля населения | `districts[].name`, `profile`, `population_share` | Те же поля |
| Оценка района | `districts[].D` | `D_after`, для сравнения `D_before` и `D_delta` |
| Название показателя | `indicators.<код>.name` | То же поле |
| Значение показателя | `indicators.<код>.value` | `indicators.<код>.after` |
| Было и изменение | До расчёта не нужны | `indicators.<код>.before`, `delta` |

`population_share` — доля: например, 0,27 отображается как 27%.

Статусы показателей: **ниже 40 — красный «Критично»; от 40 включительно до 50
не включительно — жёлтый «Требует внимания»; от 50 — «В норме»**. Цвет нужно
сопровождать текстом или символом. Чем больше любой показатель, тем лучше:
высокая «Разгрузка дорог» означает меньше пробок, а не больше.

### Каталог проектов и «Ваш план»

Сейчас каталог расположен в две колонки, выбранный план — рядом.
Есть фильтр направления и раскрывающиеся «Правила и совместимость проектов».

Карточка проекта содержит название, направление, цену, лаг, эффекты и кнопку
«Добавить проект». Для районной меры есть выбор района; городская подписана
«Действует во всех районах города». После выбора кнопка становится «В плане».

Поля карточки из `city_data.measures[]`: `id`, `name`, `direction`, `cost`,
`lag`, `effects`, `scope`. Название направления ищется в `directions`, названия
показателей эффектов — в `indicators`. Коды нужны для связи данных; пользователю
нужно объяснение вроде «Школы и детсады: +16», а не только `S1 +16`.

**Лаг** — задержка до начала работы проекта, в кварталах. Горизонт модели —
8 кварталов. В каталоге показаны полные эффекты **до учёта лага**; в результате
`measures[].effects_realized` — уже с учётом задержки. Их нельзя выдавать за
одинаковые числа или обозначать как проценты роста.

В «Вашем плане» показываются список выбранных проектов, район/«Весь город»,
цены, общая стоимость и счётчик. Действия: убрать отдельный проект, очистить
план, рассчитать результат. При добавлении пятого проекта расчёт запускается
автоматически; отдельная кнопка расчёта тоже остаётся.

Если не хватает денег, уже выбрано пять проектов, мера повторяется либо
обнаружен конфликт/лимит направления, кнопка добавления неактивна. Причина
видна рядом и в подсказке. До пяти проектов кнопка расчёта неактивна.
Окончательный вердикт всегда даёт `validate()` движка.

## Вкладка «Результаты»

До полного расчёта здесь объяснение, что нужно закончить выбор. После расчёта:

| Блок | Что показать | Поля `sample_simulation.json` |
| --- | --- | --- |
| Итог | Score и прирост относительно базы | `score`, `delta.score`, `baseline.score` |
| Стоимость | Потраченный и оставшийся бюджет | `cost`, `budget_left`, `budget` |
| Критические показатели | Сколько осталось и как изменилось | `N_crit`, `baseline.N_crit`, `delta.N_crit` |
| Таблица районов | Название, было, стало, изменение | `districts[].name`, `D_before`, `D_after`, `D_delta` |
| График | Два сопоставимых столбца «Было / Стало» для каждого района | `D_before`, `D_after` |
| Вышли из критической зоны | Район, показатель, было, стало | `critical_resolved[].district_name`, `indicator_name`, `before`, `after` |
| Остались критическими | Раскрывающийся список | `critical_indicators[].district_name`, `indicator_name`, `value` |
| Синергии | Какие меры усилили друг друга, где и с каким бонусом | `synergies[].pair`, `district_name`, `bonus`, `note` |
| Вклад проектов | Название, район, вклад в Score и реализованные эффекты | `measures[].name`, `district_name`, `score_contribution`, `effects_realized` |
| Автоматический разбор | Объяснение советника и раскрываемый журнал | Отдельный `sample_advisor.json` |

Пустые списки означают отдельные состояния: «Синергии не сработали», «Ни один
показатель не вышел из критической зоны». Ноль критических показателей —
успешный результат, а не отсутствие данных. `critical_new` позволяет отдельно
обозначить новые провалы; сейчас они входят в общий список критических.

Вклад меры — разница между оценкой полного плана и оценкой без этой меры,
включая потерю её синергий. **Сумма вкладов не обязана равняться приросту Score**:
не нужно изображать её как точное разложение прироста в накопительной диаграмме.

Дополнительно движок отдаёт `D_avg` (средняя оценка районов с учётом населения),
`min_district` (слабейший район), `score_breakdown` (подстановка в формулу),
`directions_coverage` и `notes`. Это доступные данные для пояснений; отдельных
обязательных блоков под каждое из этих полей в текущем интерфейсе нет.

## Вкладка «Лучшие планы»

Кнопка «Найти лучший план» запускает поиск. Пока он работает, показывается
индикатор ожидания. Затем появляются пять карточек: номер, Score, изменение
от базы, стоимость, состав проектов и кнопка «Применить».

Поля `sample_optimize.json`: список `results`; в каждой записи — `rank`,
`score`, `score_delta`, `cost`, `budget_left`, `decisions`. Названия проектов
для `decisions[].measure` берутся из каталога, название района — по
`decisions[].district`. `null` означает весь город. `summary` — готовое краткое
описание состава; `message`, `errors`, `stats` — сведения о результате поиска.

«Применить» **заменяет** текущий план, проверяет его и запускает расчёт.
Карта, профиль и разбор переключаются на новый результат. Основная кнопка
ищет среди всех проектов, не закрепляя уже выбранные. Отдельных полей
ограничений на этой вкладке сейчас нет: исключения, обязательные меры и
меньший бюджет можно задавать текстом в чате советника.

Нужны состояния «поиск выполняется», «нет допустимых планов», «ошибка поиска».
`stats.seconds` — время конкретного запуска, а не фиксированная цифра макета.

## Вкладка «ИИ-советник» и автоматический разбор

После успешного расчёта советник сам готовит разбор, без вопроса пользователя.
Этот же разбор виден в «Результатах» и в начале чата. Затем пользователь может
задать вопрос или ограничения для альтернативы, например: «Без ЛРТ, школу
в Нуру, бюджет до 80 у.е.». Есть кнопка «Обновить разбор».

Структура общего разбора: **итог → сильные стороны → риски и компромиссы →
последствия для жителей → как улучшить**. Нужно предусмотреть отрицательные
эффекты отдельных мер, слабейший район, остаток бюджета, сохраняющиеся
критические показатели. Текст должен оставаться читабельным, даже если он
длиннее карточки; нельзя обрезать риски ради красивой короткой цитаты.

| Поле `sample_advisor.json` | Использование |
| --- | --- |
| `answer` | Основной текст, поддерживает абзацы и жирные подписи Markdown |
| `offline` | Признак шаблонного ответа без LLM |
| `notice` | Видимая пометка «Советник работает в офлайн-режиме» |
| `reason` | Короткое пояснение причины резервного режима |
| `tool_calls[]` | Содержимое блока «Как советник пришёл к выводу» |
| `tool_calls[].name` | Имя инструмента: baseline / validate / simulate / optimize |
| `arguments` | Переданные параметры, например состав плана или ограничения |
| `summary`, `result` | Краткий результат словами и структурированными полями |
| `source` | `preparation` — проверка приложения; `model` — выбор ИИ |
| `status` | `ok` — успех; `invalid` — недопустимый план; `error` — ошибка вызова |
| `evidence_id` | Служебная ссылка на результат, не основной текст для игрока |

В офлайн-примере журнал содержит настоящие вызовы `baseline`, `validate`,
`simulate`, все с `source=preparation`. **Это не действия LLM**: не подписывать
такой пример «ИИ выбрал инструменты». В онлайне дополнительные вызовы модели
помечаются `source=model`. Журнал показывает аргументы и результаты, а не
скрытый ход рассуждений модели.

LLM не считает и не придумывает цифры. Оценки, дельты, стоимости и последствия
численно подтверждаются движком. Без ключа или при сбое API разбор по шаблону
остаётся доступен с честной офлайн-пометкой. Поле ввода отключено до расчёта.
Переключение района/вкладки не должно повторно вызывать советника; изменение
плана очищает прежний разбор и историю чата.

## Как устроена география

Файл: [data/astana_districts.geojson](../../data/astana_districts.geojson).
Верхний уровень — `FeatureCollection`, внутри `features` — пять районов.
Каждый объект `Feature` содержит `geometry`, `properties` и верхнеуровневый `id`.

| Свойство исходного файла | Что означает |
| --- | --- |
| `properties.id` | Главный ключ связи с `districts[].id`: esil, almaty, saryarka, baikonur, nura |
| `properties.name` | Короткое русское название |
| `properties.name_full` | Полная подпись, например «район Нура» |
| `properties.source` | Источник геометрии; в текущем файле `fallback_approx` |
| `properties.osm_id` | Идентификатор объекта OpenStreetMap; в текущем файле `null` |
| `properties.osm_names` | Дополнительные названия из источника; сейчас пустой объект |
| `properties.area_km2` | Площадь в км²; справочное поле, сейчас не выводится в профиль |
| `properties.center_lon`, `center_lat` | Центр для позиционирования/подписи |
| `geometry.type` | Сейчас у всех `Polygon`; интерфейс также поддерживает `MultiPolygon` |
| `geometry.coordinates` | Кольца полигона; каждая точка записана как **[долгота, широта]** |

Для `Polygon` сначала идёт список колец, затем список точек каждого кольца;
первое кольцо — внешняя граница. У `MultiPolygon` добавляется уровень списка
полигонов. Контуры следует брать готовыми из файла, не рисовать по центрам.

В `metadata` есть `source`, `generated_at`, `attribution` и `note`. Текущий
файл — **приблизительные полигоны для демо, не официальные границы**. На карте
нужна подпись «Границы районов на этой карте схематичны». Площади и центры
в таком файле не следует представлять как проверенную официальную статистику.

При отображении интерфейс добавляет в копию `properties` поля `rating`
(форматированное D), `problems` (три слабых показателя), `fill_color`
(цвет RGBA), `elevation` (высота для объёма). **В исходном GeoJSON этих полей
нет**: они меняются вместе с результатом. Высота сейчас равна D × 35 для
визуального эффекта и не означает высоту зданий или объём инвестиций.
Название в подсказке берётся из справочника города по `id`.

## Обязательное поведение и состояния макетов

| Состояние | Что обязательно видно / доступно |
| --- | --- |
| Первый вход | База 52,56, бюджет 100, «0 из 5», карта/карточки и каталог |
| План не завершён | Текущая стоимость, остаток, счётчик; пояснение, почему расчёт ещё недоступен |
| Денег не хватает | Неактивное добавление с причиной; превышение бюджета не разрешается |
| Выбрано пять мер | Новую меру не добавить; можно удалить/заменить, идёт проверка и расчёт |
| Нарушено правило | Все ошибки `errors[]` по-русски; недопустимому плану не присваивать итоговый Score |
| Расчёт успешен | Score и дельта, «было / стало», обновлённая карта, критические показатели, синергии и вклад мер |
| Есть ухудшение | Отрицательный эффект виден явно; не показывать все изменения только зелёным |
| Советник готовит ответ | Понятное состояние ожидания |
| Советник ответил | Сильные стороны, риски, последствия; журнал инструментов раскрывается |
| API отсутствует/недоступен | Офлайн-разбор и заметная пометка, приложение продолжает работать |
| География недоступна | Карточки районов и выбор через список |
| Движок недоступен | Исходные данные и сохранённый выбор; расчёт и поиск не выдаются за выполненные |
| План изменён | Старые итог, цвета результата и объяснение больше не относятся к новому выбору; до пересчёта показывается база |
| План оптимизатора применён | Полная замена выбора, пересчёт и новый разбор |

Правила, которые нельзя потерять при редизайне: ровно пять **разных** проектов;
сумма не выше 100; не более двух мер одного направления; район обязателен
для районной меры, для городской отсутствует. Не требуется выбрать по одной
мере из каждого направления. Несовместимы M1 + M3 в любом размещении,
M4 + M7 в одном районе, M5 + M13 в одном районе. Остаток денег не даёт бонуса.

Синергии: M1 + M2 усиливают разгрузку дорог в районе M1; M10 + M12 —
безопасность улиц в районе M10; M5 + M6 — качество воздуха в районе M5.
Размеры фактически сработавших бонусов берутся из `synergies[].bonus`.

Все основные подписи, ошибки и пояснения — по-русски. Длинные названия
проектов и показателей должны переноситься, а не исчезать. Значение, единицы,
знак изменения и его смысл должны читаться и без различения цветов.

## Готовые сценарии для макетов

**Успешный пример из ТЗ:** M7, M8 и M10 — в Нуре; M12 — весь город; M5 —
в Сарыарке. Стоимость 95, остаток 5, Score 56,54, изменение +3,99 от базы 52,56.
Оценка Нуры меняется с 49,18 до 52,96. Срабатывает синергия M10 + M12.
Из критической зоны выходят школы/детсады (38 → 48) и медицина (35 → 43,75)
в Нуре. Они остаются **жёлтыми**, потому что ещё ниже 50: выход из критической
зоны не равен статусу «В норме».

**Невалидный пример:** M4 и M7 — в Нуре; M3 — в Есиле; M13 — в Алматы;
M12 — весь город. Выбрано ровно пять, но стоимость 111 при бюджете 100 и
парк конфликтует со школой в Нуре. Показываются обе ошибки из
`sample_invalid.json`. Это пример состояния ошибки, а не обычный путь через
каталог: текущие быстрые подсказки уже блокируют добавление таких сочетаний.

**Лучший план текущего поиска:** первая карточка в `sample_optimize.json` —
Score 57,24, стоимость 98, остаток 2. Для остальных карточек используйте
остальные записи `results`, не создавайте собственные оценки.

**Офлайн-советник:** используйте полный текст из `sample_advisor.answer`,
пометку `notice` и реальные три записи журнала. Для этого макета не нужен ключ API.

## Как обновить примеры — для разработчика

Из корня проекта, в окружении с зависимостями проекта и советника:

```powershell
python -B docs/for_designer/generate_samples.py
```

При необходимости зависимости устанавливаются из существующих
`requirements.txt` и `requirements-ui.txt`. Скрипт читает актуальные данные,
выполняет реальные вызовы, проверяет валидность топ-5 и совпадение их оценок
с `simulate`, затем перезаписывает только пять `sample_*.json` в этой папке.
Советник принудительно работает офлайн; `.env` не читается, API не вызывается.
Байткод в `engine/`, `agent/` и `ui/` не создаётся.

Время поиска в `stats.seconds` может отличаться при повторной генерации —
оно сохранено как вернул движок. После изменений модели числовые примеры
в этом брифе нужно сверить с обновлёнными JSON. Для переработки оформления
разработчик использует `ui/style.css`; в рамках подготовки этих материалов
код приложения и стили не менялись.
